# Flutter 校园数据的短期前台内存复用

## Status
Superseded by [0035](0035-campus-device-snapshot-and-schedule-widgets.md)
Class: architecture

## Context and Problem Statement

校园底栏切换会销毁私密视图，返回时重复请求学校数据。需要让返回与刷新更顺畅，同时保持校园凭据只在服务端、学业记录不进入设备持久化存储的边界。

## Decision Drivers

- 减少短时间底栏往返的重复学校请求，今日课表优先展示。
- 复用前核验当前论坛会话和学校绑定，避免跨账号或旧身份数据残留。
- 避免跨日课表及长期未刷新的消息；缓存保留时间不因读取延长。
- 保持后台清理、取消请求、迟到响应隔离与现有 HTTP `private, no-store` 语义。

## Considered Options

- 页面销毁时丢弃全部数据，返回始终重新请求。
- 将指定数据集短期保留在独立前台内存缓存，视图继续按页面生命周期销毁。
- 将校园数据写入设备数据库，提供重启后的离线访问。

## Decision Outcome

选择独立、最多五分钟的前台内存缓存，保留资料、校历、课表和消息列表的白名单投影。成绩、消息正文与学校凭据不进入缓存。缓存从请求开始计时，读取不续期，定时器在没有页面监听时仍移除到期条目。

页面仍可在离开校园标签时销毁并取消请求。返回时先请求绑定状态，再按会话、站点与绑定版本复用尚未过期的数据；成绩等其他数据继续采用页面内存生命周期。后台、会话变更、解绑、换绑和授权失效使缓存失效，在途请求通过版本隔离拒绝迟到写入。教学日相关数据不能跨上海午夜复用，可见页面负责检查更新，隐藏页面不轮询。

手动刷新保留同一身份的现有展示并显示进度。核验发现身份变化或核验失败时清空数据；区块读取失败时移除其旧数据并显示错误。服务端 API、凭据处理和 `no-store` 响应不变；该机制不承诺离线可用。

## Pros and Cons of the Options

- 页面内存：清理边界简单，但底栏快速往返也要重新加载全部数据。
- 有界前台内存：满足快速返回和刷新体验，保留无持久化设计；代价是增加绑定校验、到期与生命周期隔离逻辑，并容许五分钟内的数据延迟。
- 本地数据库：支持重启与断网阅读，但需要持久化保护、用户管理和清除规则，超出减少重复加载的需求。
